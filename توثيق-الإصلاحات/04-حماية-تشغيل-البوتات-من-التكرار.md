# منع تشغيل البوتات مرتين عند تعدد الـ workers

## المشكلة
عند تشغيل التطبيق، `restore_all_bots()` تُستدعى تلقائياً في `app/__init__.py` عشان تعيد تشغيل كل البوتات اللي كانت مفعّلة (`is_active = TRUE`). لو gunicorn شغّال بأكثر من worker واحد، كل worker عنده نسخته الخاصة من الذاكرة (`_running_bots`)، فكل worker يستدعي `restore_all_bots()` بشكل مستقل ويحاول يشغّل **نفس البوت** بـ `infinity_polling()`.

النتيجة: تيليجرام يرفض بخطأ `Conflict: terminated by other getUpdates request` لأن أكثر من اتصال يحاول يسحب تحديثات نفس البوت بنفس الوقت — وردود البوت تصير عشوائية/متقطعة.

كان فيه إعداد `BOT_WORKER = True` مضاف مسبقاً بـ `settings.py` مع تعليق "شغّل البوتات فقط من worker رقم 1" — لكنه ما كان مستخدم بأي مكان بالكود.

## الحل
استخدام قفل موزّع بسيط عبر Redis (المشروع أصلاً يستخدم Redis للجلسات، فلا حاجة لأي بنية تحتية جديدة). أول worker يوصل لهذا الكود ينجح بأخذ القفل، والباقي يتجاهلون إعادة التشغيل:

```python
def restore_all_bots():
    from app.models.bot_model import Bot
    from app.config import settings

    if not settings.BOT_WORKER:
        return

    if settings.SESSION_REDIS:
        acquired = settings.SESSION_REDIS.set("sadim:bots:worker_lock", "1", nx=True, ex=3600)
        if not acquired:
            return  # عملية/worker ثانية شغّلت البوتات بالفعل

    bots = Bot.get_all()
    for b in bots:
        if b.is_active:
            start_bot(b.bot_token, b.channel)
```

- `nx=True` يعني "خزّن بس إذا المفتاح مو موجود أصلاً" — أول worker يوصل يفوز.
- `ex=3600` مدة صلاحية القفل ساعة، حتى لو انحذف Redis أو أعيد تشغيله يوماً ما، ما يضل القفل عالق للأبد.

**تحديث بعد أول تجربة تشغيل محلي:** لو Redis مو شغّال (مثلاً بيئة تطوير محلية بدون Redis server)، محاولة `.set()` ترمي `redis.exceptions.ConnectionError` وتطيح التطبيق كامل عند الإقلاع. تم لف المحاولة بـ `try/except redis.exceptions.RedisError` — لو تعذر الاتصال بـ Redis، تتوصّل رسالة تحذير بالـ console والتطبيق يكمل عادي (بدون قفل، يعني كل worker يشغّل البوتات لحاله — نفس السلوك القديم قبل هذا الإصلاح، فقط بدون كراش).

**تحديث ثانٍ — نفس المشكلة تظهر محلياً حتى بدون أكثر من worker:** عند تشغيل `python run.py` بوضع `debug=True`، Werkzeug (سيرفر التطوير) يشغّل الملف **مرتين** فعلياً — عملية "مراقبة" تراقب تغيّر الملفات، وعملية "تنفيذ" فعلية تخدم الطلبات (خاصية auto-reload). بما إن `restore_all_bots()` تشتغل عند استيراد التطبيق (سطر واحد بأول الملف)، كلا العمليتين تستوردان التطبيق وتشغّلان نفس البوت، فيصير نفس تضارب الـ 409 اللي نحاول نمنعه بالإنتاج — بس هذا سببه الـ reloader مو تعدد الـ workers.

**الحل:** تعطيل الـ reloader في `run.py` (`use_reloader=False`) — يبقى `debug=True` شغال (صفحة الأخطاء التفاعلية تشتغل عادي)، بس ما يعيد التطبيق تشغيل نفسه تلقائياً عند تعديل ملف. الأثر الجانبي: لازم توقف وتشغّل `python run.py` يدوياً بعد أي تعديل بالكود وقت التطوير المحلي (بدل ما يعيد نفسه تلقائياً).

## قيد مهم لسا موجود (غير محلول بهذا التعديل)
هذا الحل يمنع تكرار **بدء التشغيل الأولي** بس. عمليات "تشغيل/إيقاف/حذف بوت" اللي يسويها المستخدم من لوحة التحكم (`/bots/toggle`, `/bots/delete`, `/bots/add`) لسا تعتمد على إن نفس الـ worker اللي فيه ذاكرة `_running_bots` الخاصة بذاك البوت هو اللي يستقبل الطلب. مثال: لو `restore_all_bots()` شغّلت بوت معيّن على Worker A (لأنه فاز بالقفل)، ثم طلب "إيقاف" لنفس البوت وصل لـ Worker B — عند Worker B القاموس ما فيه هذا التوكن أصلاً، فـ `stop_bot()` ما راح تعمل شي فعلي (البوت يضل شغال على Worker A).

**الحل الكامل لهذا** يحتاج تنسيق حالة موزّعة بين كل الـ workers لكل عملية (مثلاً: نقل تشغيل البوتات لعملية/خدمة منفصلة عن Flask تماماً، أو استخدام طابور مهام). هذا خارج نطاق إصلاح باگ ويحتاج قرار معماري لاحق.

**التوصية الحالية**: لحد ما يتم تطوير حل معماري كامل، شغّل gunicorn بـ `--workers 1` (worker واحد فقط) — هذا يخلي كل شي (تشغيل، إيقاف، حذف) يشتغل بشكل صحيح ومتسق دايماً لأنه ما فيه إلا نسخة وحدة من الذاكرة أصلاً.
